Effective limits in this checkout

  • Provider route: ≤ 6 admitted calls per goal, goal worker bound 1–6, maxActiveRuns 1.
  • Diagnostic native-Codex cloud selection (disabled for normal product goals): controller worker cap 1; no relay. This branch is not qualified as a working remote subscription team.
  • Product API-model cloud selection: configured worker cap clamped to 1–6 (default 3); relay created only if cap > 1. Depth and children are bounded, with maxActiveRuns 2.
  • The fleet worker cap excludes the enrolled local root. Fly workers consume that child-worker bound; the separate relay Machine is outside the worker roster.
  • Product worker flow settings: agentTurns 6, leadTurns 12, local subflow concurrency 1. Recovered generic template default is up to 10 local agents; the product override is the applicable bound.
  • Unknown run, spend, capture or cleanup outcomes retain original identities and can hold further admission. A stop request is not a receipt proving remote cancellation.

Architecture evidence and current qualification

This diagram was derived from the checked-out source and sanitized acceptance notes. It is not a live deployment inventory. No service startup, provider execution, account-state inspection, resource creation or deployment was performed to make it.

Local desktop

Sandboxed renderer, trusted runtime, loopback API, provider manager, persistent conversation / goals and a bounded provider team. Native Codex artifact generation and independent review are live verified in the release notes.

Local FLUJO instances

The configured loopback source is an optional dependency. A separate isolated diagnostic instance was used and stopped according to acceptance notes. Instance identifiers, addresses and present liveness are not established here.

Cloud / provider availability

An isolated Fly worker reached ready but its team conversation failed. Complete cloud output, tool-enabled FLUJO/Codex compatibility, cloned refresh and PC-off continuation remain unqualified. Claude subscription execution was denied on the validation host; API routes have deterministic fixtures. Antigravity unattended execution is unsupported.

MCP inventory

bash, filesystem, flujo and optional browser are bundled workspace servers. fleet is a streamable HTTP MCP endpoint implemented by the local controller and reached through the relay where available. Extra MCPs and their accounts are conditional; no real inventory was read.

Trust and data boundaries

  • The local computer boundary encloses all host processes, including local MCP subprocesses when used. Their accessible files follow configured allowed paths; a workspace alone does not provide OS isolation.
  • The remote Machine boundary encloses its FLUJO instance, worker workspace, own MCP processes and volume. Agents in one worker share its filesystem. Sibling Fly workers do not share a filesystem.
  • The fleet registry / board is host-authoritative. Workers reach it using actor credentials. A relay transports requests, preserving worker authorization for the controller.
  • The cloud clone path crosses a trust boundary using the upstream private snapshot mechanism. Credential stores stay outside Git; the diagram does not claim remote login refresh is safe or qualified.
  • Reported, estimated, unknown and subscription usage remain separate. Estimated spend is not billed spend; deterministic fixtures are not live provider runs.
  • Existing production fleets remain under their owners. This diagram does not imply their adoption or new authority over them.
